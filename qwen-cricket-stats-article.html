Teaching Qwen to Answer Cricket Statistics Questions with SQL

How a local language model, a domain-specific prompt guide, deterministic name resolution, SQLite, and regression testing became a practical cricket research assistant.

6A project field note · 12 minute read

Cricket statistics questions sound simple until you try to translate them into database queries. “Who dismissed Gavaskar most often?” and “Which visiting batter scored the most Test centuries in Australia?” require much more than knowing SQL syntax.

The system must understand cricket terminology, resolve historical player names, choose the right level of aggregation, distinguish opposition from location, and avoid silently plausible but incorrect queries. I built a local assistant using Qwen, Ollama, Python, and SQLite to explore how prompt engineering can bridge that gap.

Qwen’s job is not to memorize every cricket record. Its job is to translate a cricket question into accurate SQL over a trusted database.

The architecture

Natural-language cricket question↓ Player, team, and intent resolution↓ Schema + cricket SQL guide + prompt rules↓ Qwen 2.5 Coder through local Ollama↓ Generated SQLite SELECT query↓ Safety checks + database execution↓ Cricket statistics answer

The model runs locally through Ollama as qwen2.5-coder:14b. The Python application sends a prompt to the Ollama generation API on localhost:11434. SQLite—not the language model—remains the factual source of truth.

Designing the cricket database

The database combines Cricsheet-style JSON with historical CricketArchive scorecards. Its normalized tables represent several different grains:

  • match_stats: one row per match
  • match_innings_stats: one row per team innings
  • player_match_stats: one row per player per match
  • player_match_innings_stats: one row per player per innings
  • player_batting_innings_stats: one row per batting innings
  • player_career_stats: career summaries
  • player_career_group_stats: opposition, year, and competition summaries

This structure is central to text-to-SQL accuracy. “Kapil Dev’s total Test wickets” belongs in a career table. “Five wickets in an innings” requires an innings-level bowling table. “India’s highest Test total” requires team innings joined to match metadata.

Why the schema was not enough

Column names do not teach cricket semantics. The model needs to know that a Test can contain four team innings, that a player can bat twice, and that a batting average is runs divided by dismissals rather than runs divided by balls.

The project therefore includes a prompt-augmentation document called cricket_sql_guide.md. It explains table selection, cricket concepts, name rules, locations, common query patterns, and known failure modes.

Example prompt rule For a player’s Test career wickets, select player_career_stats.wickets_taken from the competition_name = 'All' row. Never use COUNT(*), because that counts career rows rather than wickets.

Without this rule, a model can produce syntactically correct SQL that returns “1”—the number of matching career rows—instead of Kapil Dev’s actual wicket total.

SELECT wickets_taken AS total_wickets
FROM player_career_stats
WHERE player_name = 'Kapil Dev'
  AND format_group = 'Test'
  AND competition_name = 'All'
ORDER BY wickets_taken DESC, matches DESC
LIMIT 1;

Player-name resolution was harder than SQL

Fans ask about Sachin Tendulkar, Sunil Gavaskar, Don Bradman, and Vijay Hazare. Historical databases may store them as SR Tendulkar, SM Gavaskar, DG Bradman, and VS Hazare.

Older scorecards can also split one person across an initialed batting identity and a surname-only bowling identity. The correct database row can depend on whether the question concerns batting, bowling, or fielding.

Instead of asking Qwen to invent a database name, Python performs deterministic preprocessing:

  • Known aliases
  • Exact full-name matches
  • Initial-plus-surname matching
  • Surname and fuzzy matching
  • Test-career filtering
  • Statistic-aware ranking

The resolved identity is inserted into the prompt as explicit context, such as Use player_name = 'SM Gavaskar'.

Cricket language is contextual

“Against” means opposition

“How many Test hundreds did Gavaskar score against Australia?” requires opposition = 'Australia'. It does not mean the player represented a team other than Australia.

“In India” means match location

“Did Bradman play a Test in India?” asks where the match occurred. It requires match metadata and city or venue filtering, not a player-team predicate.

“Visiting” combines location and nationality

A visiting batter in Australia must have played at an Australian location while representing a team other than Australia.

“Overseas” depends on the player

For Gavaskar, overseas means outside India. For Bradman, it means outside Australia. A single hard-coded country exclusion cannot answer both correctly.

The trace–diagnose–improve loop

The assistant was improved through a manual feedback workflow. I would run ask_cricket.py, ask a real cricket question, and inspect any incorrect query or result.

  1. Write an authoritative SQL query manually.
  2. Run it against SQLite and confirm the expected result.
  3. Compare it with Qwen’s generated SQL.
  4. Classify the failure.
  5. Fix the correct layer.
  6. Add the question to the regression suite.
  7. Run every existing evaluation again.

When tracing is enabled, the application records the question, resolved context, full prompt, Qwen response, cleaned SQL, returned rows, and timing in JSONL. Without tracing, the generated SQL and displayed result can be supplied manually for analysis.

Failures that taught useful lessons

Ignoring a named team

For “What is India’s highest total in a Test innings?”, Qwen initially reused the general highest-innings pattern and returned Sri Lanka’s overall record. The missing clause was:

AND mi.team = 'India'

The reusable lesson was added to both the cricket guide and the primary prompt: when a highest team-innings question names a team, the final SQL must filter to that team.

Treating a null winner as a team

For “Which team has won the most Test matches?”, Qwen grouped every value in match_stats.winner. Matches without a recorded winner created a large null group that outranked real teams.

WHERE match_type = 'Test'
  AND winner IS NOT NULL
  AND trim(winner) <> ''
GROUP BY winner
ORDER BY COUNT(*) DESC;

Summing an already-stored career total

For MS Dhoni’s Test stumpings, Qwen used SUM(stumpings) on the career table. It happened to return the right value with one matching row, but the reasoning was wrong. Career totals such as catches and stumpings should be selected directly.

Confusing the batter and bowler

In “Which bowler dismissed Gavaskar most often?”, Gavaskar is the dismissed batter. The query filters the batter row and groups by dismissal_bowler. Using wickets_taken answers a different question.

Building the regression suite

The evaluation suite grew from 20 to 30 database-grounded cases. It now covers career batting and bowling, name aliases, dismissals, overseas records, both-innings centuries, team totals, venues, match margins, fielding, chronology, and player comparisons.

Each case can verify required and forbidden SQL fragments, row counts, scalar values, or expected rows. The expected answers are computed from SQLite, never copied from Qwen.

{
  "name": "india_highest_test_innings_uses_team_innings",
  "question": "what is india's highest total in a test innings",
  "sql_contains": [
    "FROM match_innings_stats",
    "JOIN match_stats",
    "team = 'India'"
  ],
  "first_row": {
    "team": "India",
    "total_runs": 759
  }
}

The final expanded run produced semantically correct answers for all 30 cases while preserving the original 20.

Do not make evals more rigid than the problem

A correct answer can come from different SQL formulations. Lara’s highest Test score can be selected from a career summary or calculated with MAX(runs_scored) over Test innings. A result column may be called winner or aliased as team.

Early assertions sometimes treated these harmless differences as failures. The suite was refined to emphasize:

  • The correct result
  • The correct filters and aggregation level
  • The absence of known dangerous patterns
  • Semantic correctness rather than one exact SQL string

What local inference means

Local inference is the stage where Qwen reads the question, schema, guide, resolved entities, and recent context, then generates SQL. SQLite execution is generally fast; most evaluation time is spent processing the large prompt and generating model output.

This creates a trade-off. Adding rules can improve accuracy, but a growing prompt increases latency and makes critical instructions easier to overlook. High-value constraints were promoted into the primary instruction block, while detailed examples remain in the longer guide.

Prompt engineering or fine-tuning?

Prompt engineering is the right starting point here. The schema changes, failures are inspectable, rules can be updated immediately, and deterministic code handles entity resolution better than a probabilistic model.

Fine-tuning may become useful after collecting hundreds or thousands of reviewed question-to-SQL pairs. Until then, prompt augmentation is easier to maintain and debug.

Schema is not semantics

The model needs cricket concepts and aggregation rules, not only table definitions.

Resolve names deterministically

Do not ask the model to guess the exact player identity stored in the database.

Fix the right layer

Use Python for entities, prompts for domain reasoning, and data repairs for data problems.

Ground every expected answer

Regression values must come from authoritative SQL over the current database.

Test semantic equivalence

Allow multiple correct SQL forms while rejecting incorrect reasoning.

Protect every learned behavior

Each real failure becomes a permanent regression case.

Conclusion

The useful intelligence in this assistant is distributed across the system. Qwen provides flexible language interpretation. Python resolves entities and adds deterministic context. The cricket guide supplies domain knowledge. SQLite produces the facts. The eval suite prevents yesterday’s fixes from becoming tomorrow’s regressions.

That combination—local inference, domain-aware prompt augmentation, deterministic preprocessing, database verification, and disciplined evaluation—turns a general coding model into a practical cricket statistics assistant.
